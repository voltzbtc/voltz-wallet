# Internationalisation

The app is international. Every locale it ships is a first-class target, and a screen has to work
from start to finish in any of them.

## Strings

- Every string a user can see goes through i18next (`t(...)` from react-i18next). A temporary or
  placeholder string follows the same rule.
- Locales live in `src/i18n/locales/`, one JSON file per locale, 24 of them. `en-US.json` is the
  reference, and `__tests__/locales.test.ts` fails when any locale is missing a key, carries an extra
  one, changes an interpolation placeholder or contains an em dash. The test discovers the files, so
  a new locale is covered as soon as it exists.
- Plurals use i18next's suffixes, called as `t('welcome.words', { count })`, never a number spliced
  into a fixed sentence. Each locale carries one form per CLDR plural category of its language, as
  `Intl.PluralRules` reports them: `_one` and `_other` in English, German, Turkish, Hindi and Urdu,
  `_one`, `_few`, `_many` and `_other` in Russian and Polish, all six from `_zero` to `_other` in
  Arabic, `_one`, `_two` and `_other` in Hebrew, `_many` for a round million in Portuguese, Spanish,
  French and Italian, and `_other` alone in Chinese, Japanese, Korean, Thai, Vietnamese and
  Indonesian. A form the locale lacks renders from en-US, so the locale test fails on a missing form
  and on one the language never uses, naming the key. In Russian and Polish `_other` is reached only
  by a fraction (`1,5 слова`), and in the Romance languages `_many` reads as "a million of"
  (`1000000 de palavras`).
- Hermes ships `Intl` without `PluralRules`, on iOS and on Android, and i18next then applies
  English's rule to every language, `one` for 1 and `other` for anything else, while Jest on Node
  picks the CLDR category. `src/i18n/pluralRules.ts` carries CLDR's cardinal rules for the shipped
  languages and installs them before i18next starts, only where the engine has none.
  `__tests__/pluralRules.test.ts` holds them to Node's ICU for every locale file, so a new language
  whose rule is not English's fails there until it gets its own, and it fails when the app's i18next
  is loaded without them. The Hermes the app ships (250829098.0.14) was read on 2026-11-16: its iOS
  and Android binaries name `NumberFormat` and `DateTimeFormat` and never `PluralRules`. On
  2026-09-29 the same version on the iOS simulator had no `Intl.PluralRules` and gave ICU's answer
  with these rules for all 24 locales.
- Keys under `push.*` are filled by the push notification gateway rather than by i18next, and they
  use single braces (`{domain}`). The locale test checks those placeholders as well.
- User-facing text contains no em dash in any language.
- Devanagari, Thai and Vietnamese draw marks above the capital height, and a line box no taller
  than the font size cuts them. A text takes its line height from `font.leading` or from the
  engine; see Vertical rhythm in [design-system.md](design-system.md).
- German addresses the reader with du in every string. A capitalised Sie or Ihr stays only where it
  opens a sentence and means they or it, as in `receive.modeCharge` ("They pay").

## Language selection

- `src/i18n/index.ts` picks the starting language with `RNLocalize.findBestLanguageTag` over the
  bundled locales, and starts in `en-US` when nothing matches (`__tests__/i18nStart.test.ts`).
- `fallbackLng` is `en-US` as well, so a key missing from a locale renders in English.
- A language chosen in the app is stored and applied at boot by `App.tsx`.

## Numbers, currency and dates

Translation is not enough; formats follow the locale too.

- Every number is written with the app language's separators, as CLDR writes them with Latin
  digits: bitcoin and token amounts, and every currency, BRL and USD included. Sats are the one
  exception. They keep the Bitcoin convention in every language, a no-break space between groups
  (`47 112 sats`), so a figure in sats never reads like a decimal, and `formatSats` draws them that
  way wherever they appear. Portuguese
  (Brazil) writes `1.234,56`, English `1,234.56`, French `1 234,56` with a narrow no-break space,
  Hindi groups `12,34,567`, and Spanish, Italian, Polish and European Portuguese leave four digits
  ungrouped (`1234`, `12.345`). The separators come from a table in `src/wallet/fiat.ts` rather than
  from Intl at run time, so a device writes what the tests measure whatever Intl its JavaScript
  engine ships, and `fiat.test.ts` checks the table against CLDR for every shipped language. The
  table follows i18next from boot through a `languageChanged` listener.
- Money follows CLDR's currency format for the language in the same way, from a second table in
  `fiat.ts` (`MONEY`) that `fiat.test.ts` checks against CLDR for every shipped language, with a
  small, a grouped, a zero and a negative amount. The language decides the side of the symbol, the
  no-break space between it and the digits, the minus sign, and the symbol of USD and BRL
  themselves. English writes `R$1,234.56`, Portuguese (Brazil) `US$ 3,15` and `R$ 1.234,56`,
  French `3,15 $US`, Italian `3,15 USD`, and Mexican Spanish `USD 3.15`, since `$` there is the
  peso. Arabic and Hebrew put the symbol after the digits and open the amount with a right-to-left
  mark, Urdu puts it before, and all three write the minus with a left-to-right mark, as CLDR does.
- A bare `$` is the dollar of whoever reads it, so it is written only for the device's own currency:
  the first code react-native-localize's `getCurrencies()` reports, the same one that picks the
  default display currency. `src/i18n` reads it when it loads and again whenever the app returns to
  the foreground, and hands it to `fiat.ts` through `setLocalCurrency`. On a device whose own
  currency is USD, English writes `$3.15` and German `3,15 $`, as CLDR does. On any other device the
  eight languages whose CLDR symbol for USD is the bare `$` (English as en-US, German, Russian,
  Turkish, Hindi, Japanese, Urdu and Hebrew) write CLDR root's `US$` in its place, on the same side
  and with the same spacing, so an Australian device in English reads `US$3.15`, as CLDR en-001
  writes it. A currency the feed gives only a bare `$` (MXN, ARS, CLP and the other pesos) keeps
  that `$` on its own device and is named by its code on every other one, so a Mexican device in
  Mexican Spanish reads `$1,234.50` for pesos and `USD 3.15` for dollars, and the same pesos read
  `MXN 1,234.50` on a US device. A device that names no currency writes no bare `$` at all. The rule
  lives in `fiatSymbol`, which every path that draws a symbol goes through (`formatFiat`, the amount
  sheet's `fiatAffixes` and its unit button), and `fiat.test.ts` checks it in every shipped
  language. A region changed in the system settings while the app was in the background is read on
  the return and reaches the next amount drawn (`i18nStart.test.ts`).
- Currency is any code the SDK's fiat feed returns, not a fixed list. `formatFiat` takes the symbol
  and the number of decimals from the feed, and the side and the spacing from the language, because
  CLDR places every currency by the language that reads it: German writes `3,15 €` and English
  `€3.15`. The feed's own placement is its home country's habit and is not used. Where the language
  sets the symbol against the digits, a symbol takes a no-break space unless the character that
  touches the digits is itself a symbol or a space, as CLDR's currency spacing does (`CHF 3.15`, but
  `€3.15`). A letter, a digit or punctuation does not count as a symbol, so BYN's `р.` is spaced as
  well. The feed's symbol is the same in every language, since only USD and BRL have a table. The
  feed prefers a disambiguated glyph (`A$`), and a currency it gives only a bare `$` follows the rule
  above. The amount sheet draws the symbol of a typed amount on the same side, through
  `fiatAffixes`. The currency picker names each currency with the feed's English name and its code
  in every language, since Hermes ships no `Intl.DisplayNames` (absent from the engine on iOS and
  Android, as `Intl.PluralRules` is).
- Amounts in the model are built with a dot and no grouping, which is what parsing, payment URIs and
  the SDK read, and take the language's separators only where they are drawn, through
  `localizeAmount`, or `formatSats` for sats, and `formatRowAmount` picks between them for a list row. The keypad draws the language's mark on its decimal key, while
  the value it confirms keeps the dot.
- A pegged token's balance reads in two places, and under a cent it keeps its first two significant
  digits, cut rather than rounded, so `0,00052 DePix` never reads as zero or as more than is held.
  The asset's own screen shows the exact figure. A bound in money under the currency's smallest step
  reads the same way (`formatSmallFiat`), so a minimum of one sat is never stated as zero.
- Dates and times go through `formatDate` and `formatTime` in `src/wallet/history.ts`, with the
  format and the 12 or 24 hour clock of the OS's first preferred locale (`deviceDateTimePrefs()` in
  `src/wallet/deviceLocale.ts`). On Android that is the phone's language. On iOS it is the language
  saved in the app, once there is one, since the app pins its own preferred languages to it (see the
  right-to-left section): with no explicit clock setting, an iPhone in Arabic with the app in
  Portuguese shows 22:03, not 10:03 PM.

## Right-to-left languages

Arabic, Hebrew and Urdu mirror the whole layout. `isRTL()` in `src/i18n/languages.ts` matches on the
base tag (`ar`, `he`, `ur` and `fa`), and its result drives `I18nManager.forceRTL`. Headers, the tab
bar, buttons, the drawer and every `flexDirection: 'row'` mirror on their own.

`I18nManager.isRTL` is handed to the JS runtime when it starts, and `forceRTL` only writes the flag
the next runtime reads. Changing direction therefore restarts the runtime, through `settleDirection`
in `src/i18n/directionRestart.ts`, which both the boot in `App.tsx` and `LanguageScreen` call and which
is the only writer of the native flags. It sits apart from the alignment helpers in
`src/i18n/direction.ts`, which every text imports, so those importers never load the SDK or the
settings file. Without the restart the text changes and the layout does not.

- On Android the restart is the app's own `VoltzRestart` module (`ReactHost.reload`).
  `react-native-restart` cannot start a new runtime under the New Architecture there: it falls back to
  `Activity.recreate`, which keeps the old `isRTL` and so restarted forever, and from the navigator it
  crashes in `react-native-screens`. iOS keeps `react-native-restart`, which reloads the runtime.
- A language set for the app in Android's own settings recreates the activity, as does a return to
  an app the system killed in the background. `MainActivity` hands its parent no saved state
  (`super.onCreate(null)`), so the app draws again from its boot, behind the PIN, instead of
  crashing on the restored fragments. That is a choice, measured on an API 36 emulator for both
  paths; the route the `react-native-screens` README documents keeps the state and sets
  `RNScreensFragmentFactory` as the fragment factory.
- A restart writes a marker first (`directionRestart` in the settings file). A boot that still
  disagrees and finds the marker renders as it is and clears it, so a restart that does not take costs
  one wrong layout, never a loop. A marker that cannot be written means no restart.
- A restart keeps the process, so the SDK instance the old runtime connected is disconnected first,
  or it would keep syncing next to the new one on the same seed and storage directory. The restart
  waits for that at most `DISCONNECT_BOUND_MS` (2 s), so a disconnect that hangs never blocks it,
  and a path that settles without a restart leaves the SDK connected.
- `allowRTL` always equals the target direction. Left `true`, the native check also follows the device
  and the app bundle language, so an app in English on an Arabic phone would come back RTL.
- In a debug build, a restart after the SDK has started its dev logger aborts on the next log line
  (the logger's JS side is gone). Release builds register no logger. To try the switch on a debug
  build, turn JS dev mode off so the bundle is served without `__DEV__`.

A figure's pieces do not survive the bidi algorithm in a right-to-left paragraph: `R$` has one strong
letter and a sign with no direction, so it reads `$R`, and a minus or a percent is neutral beside
digits, so `−5.61%` reads `5.61%−`. `Figure` holds each such run left to right with an isolate
(`holdDirection` in `src/i18n/direction.ts`), which leaves the amount on the side CLDR gives it and
every screen with it. An isolate and not the marks CLDR writes, since a mark before a minus still
leaves the minus to the paragraph's direction. A formatted amount inside a sentence is held where
i18next fills it in, in a right-to-left language, when its placeholder is one of the money names
(`amount`, `price`, `min`, `max`, `fee`, `sats`, `change`, `fiat`, in `holdMoneyPlaceholder`). Money goes
under one of those names; a value that is not money never does, since a DNS value, a key or a
reference also leaves through Share and mail, where an isolate would break a paste. Measured with CoreText and with Java's
`java.text.Bidi`: the unheld strings read as the walk saw them on Android and the held ones read right.

Four things do not mirror by themselves:

- On iOS, text with no `textAlign` follows the app bundle's localization, not the layout, so it stays
  on the left under RTL, and with the `ar`, `he` and `ur` `.lproj` in the bundle an iPhone set to
  Arabic would draw the app's English layout with it on the right. Every text therefore sets the
  leading edge (`leadingText` and `leadingInput` in `src/i18n/direction.ts`): `'left'` on text, which
  Fabric swaps under an RTL layout, and `'right'` or `'left'` on a `TextInput`, which it does not
  swap. `Txt`, the `MenuRow` label and `Field` do it themselves; a raw `Text` or `TextInput` puts the
  helper first in its style, so its own `textAlign` still wins and a centred text stays centred. A
  `Text` nested inside another is a run of the outer paragraph and sets no alignment, since an
  alignment on a run can replace the outer paragraph's, which is also why a `Txt` is never nested.
  `rules.naturalText` in `scripts/design-metrics.mjs` holds all of this at zero, and
  `node scripts/design-metrics.mjs` names any element that breaks it.
- The native stack header and the rest of UIKit follow the bundle's localization, not the app's
  layout. react-native-screens applies the header's `direction` only when it differs from its
  default `'ltr'` (`RNSScreenStackHeaderConfig.mm`, `updateProps`), so an LTR app never forces it:
  with the `ar` `.lproj` in the bundle, an iPhone set to Arabic with the app in Portuguese puts the
  back button on the right, its chevron pointing right. iOS picks the localization from the app's
  own `AppleLanguages` once per process, so the language saved in the app is written to it at boot
  and on every pick in the picker (`pinBundleLanguage` in `src/i18n/bundleLanguage.ts`), and from
  the next cold start the header and the back swipe follow the app. With no language saved nothing is
  written: detection reads the same preferred languages, so a language detected from the phone keeps
  following the phone, and so does one chosen for the app in the iPhone's Settings. A switch made in
  place keeps the localization the process launched with: after leaving Arabic, Hebrew or Urdu for an
  LTR language, the back button stays on the right until the app is closed and opened again. Setting
  the `UIView` appearance instead moves the back button but leaves its chevron pointing the old way.
  The permission prompts are drawn by the system in the phone's language whatever the app's is. All
  of this was measured on an iOS 26.5 simulator.
- The navigation marks (`TabIcon` names `chevron`, `chevron-left` and `arrow-left`) are flipped with
  `scaleX: -1` when `I18nManager.isRTL` is true, or they point the wrong way.
- The diagonal Send and Receive arrows (`send` and `receive`) are deliberately left unflipped. They
  mean up and down, not left and right.

The PIN and amount keypads are held left to right with `direction: 'ltr'`, because a phone keypad
reads 1 2 3 from the left in every language and a mirrored grid would read 3 2 1.

## Regional variants

Besides the base languages, the picker lists `pt-PT`, `en-GB`, `es-MX`, `fr-CA` and `zh-TW`. Each is a
real regional translation (European Portuguese vocabulary, British spelling, Traditional Chinese),
not a copy of the base. Adding a variant takes four steps:

1. Create the locale file in `src/i18n/locales/`.
2. Add a line to `LANGUAGES` in `src/i18n/languages.ts`, with the endonym as the label and a country
   for the flag.
3. Import it and add it to `resources` in `src/i18n/index.ts`.
4. Add `ios/VoltzWallet/<id>.lproj/InfoPlist.strings` with the four permission prompts, under Apple's
   identifier (`zh` is `zh-Hans`, `zh-TW` is `zh-Hant`, `en-US` is the development region `en`, as
   `bundleLocalization` in `src/i18n/languages.ts` maps them), and register it in the
   `InfoPlist.strings` variant group and `knownRegions` with the `xcodeproj` gem, never by editing
   `project.pbxproj` by hand. iOS reads these prompts from the bundle, not from i18next, so a missing
   file shows them in English.

The locale test then enforces key parity with `en-US`, and `languages.test.ts` fails until the
prompts exist and are registered, for every language in the picker. Every `.lproj` also changes which
localization iOS can pick for the app, which is why the direction rules above pin `AppleLanguages`,
set `allowRTL` to the target and give every text an explicit alignment.

## Flags

Flags are SVG, never emoji. Android has no flag emoji glyphs and renders one as two letters, so
`src/components/Flag.tsx` draws bundled SVGs from `flag-icons` (MIT) with `react-native-svg`, which
renders on both platforms. Every ISO 3166-1 alpha-2 country is bundled in `src/assets/flags/`.

- A language takes its flag from the `country` field in `languages.ts`. A language spoken across
  many nations uses the most recognisable one (Arabic uses Saudi Arabia).
- A currency takes its flag from `currencyCountry()` in `src/wallet/fiat.ts`, which maps the ISO 4217
  code to its ISO 3166 prefix. `COUNTRY_OVERRIDES` covers the codes whose prefix is not a usable
  country. ANG maps to Curaçao, since the AN code no longer exists. XOF maps to Senegal and XAF to
  Cameroon, the seats of the two CFA franc central banks.
- Other codes starting with `X` (XAU, XDR) have no flag, and `<Flag/>` draws a globe. The globe is
  also the fallback for a country with no bundled SVG. It is a last resort, not an expected state for
  a currency the feed returns.
